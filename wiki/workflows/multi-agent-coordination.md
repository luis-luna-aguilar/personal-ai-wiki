# Multi-agent coordination

Topology patterns for running several agents together: who talks to whom, how work is divided, and how conflicting output gets reconciled. Split out of [Agentic orchestration patterns](agentic-orchestration-patterns.md), which now covers context/harness, evaluation, and production patterns instead. See [Agent loop design](agent-loop-design.md) for how a single agent's own loop is structured.

## Coordination patterns

### Topology and routing

- **Fold before you split.** Anthropic's Applied AI team finds that one agent with skills and tool search often beats orchestrator-plus-specialist designs in enterprise deployments. Keep subagents for context bloat, parallel throwaway contexts, or tool-selection conflicts, and divide them by context, not by problem type or owning team. The fold-back recipe is on [Agent loop design](agent-loop-design.md#folding-subagents-into-one-loop).
- **Graph vocabulary and the fake-edge test.** A workflow graph has two parts: a node is one bounded unit of work with a single input and output, and an edge is a genuine data dependency, not just sequence — the second node must actually consume what the first produced. Test any hand-written workflow by walking each consecutive pair of steps and asking whether the later one truly needs the earlier one's output; steps that only run in order because that's how they were typed ("fake edges") should run in parallel instead — almost any hand-written workflow turns up two or three. Mixing deterministic and AI-driven nodes in the same graph works the same way: a step that must never be skipped or reordered is just a node with a real edge into it. *Source: Mahax (@Mahaximus_) X Article, "Graph Engineering with Claude," July 2026*
- **The diamond and the checker node.** The fan-out/fan-in "diamond" — one node splits into independent parallel nodes that a single node recombines — is the same shape as Agentic MapReduce's Map→Reduce and Glasswing's Hunt→Dedupe above; it only wins when the parallel nodes are genuinely independent and the combining node needs all of them. A **checker node**, sitting between the parallel layer and the combining node, screens each parallel output (empty, contradictory, off-topic, low-confidence, malformed) before it can silently corrupt the combined result — the same job Glasswing's Validate stage and Security Swarm's Verify stage already do above, named here as a reusable graph primitive.
- **Static graph first, dynamic only under pressure.** Start with a static graph — nodes and dependencies fixed before the run starts — because it is faster to build, more predictable, and easier to audit; reach for a dynamic graph, where a node's own output decides what runs next, only once the scope of the work genuinely can't be known upfront. Avoid dynamic graphs wherever the run must be fully auditable afterward, since the structure that actually executed isn't the one that was planned.
- **Coordinator-specialist routing.** Replace "god agents" with a coordinator that routes between smaller specialists with narrower context, tools, and responsibilities.
- **Single-agent-first escalation threshold.** Start with a single-agent system and only introduce manager/sub-agent or decentralized multi-agent topologies once tool sprawl or prompt bloat makes the single-agent design unmanageable — treat multi-agent orchestration as an escalation, not a default starting architecture. *Source: Cameron Wolfe (@cwolferesearch) synthesis via AINews, May 2026*
- **Narrow-scope parallel agents outperform exhaustive single agents in high-coverage tasks.** Cloudflare's Project Glasswing harness (8 stages, ~50 concurrent Mythos Preview agents) demonstrates this at security-research scale: each agent has one tightly scoped attack class + one target area; an independent adversarial agent validates but cannot emit new findings; root-cause deduplication collapses variant findings. The Trace stage further splits "is this buggy?" from "can an attacker reach this bug?" — a clean instance of decomposing a compound question into two separately answerable ones.
- **Model-pool routing by an AI-managed orchestrator.** Rather than hardcoding which model handles which task, a coordinator layer (e.g., Sakana Conductor) selects from a pool of available models based on the task type, cost, and current model availability. The coordinator decides routing; specialized models handle execution.
- **Mayor + polecats (one pet + many cattle).** One persistent, named supervisor agent (the "mayor") that a human interacts with directly. The mayor routes work to many anonymous, disposable worker agents ("polecats") that each handle one scoped task and shut down. The human manages one conversation; the mayor manages coordination and worker lifecycle. Workers don't accumulate context or interfere with each other — fresh start per task. *Source: Gas City workshop, Every (2026-05-19)*

### Coordination mechanics

Cursor's long-running swarm lessons (recursive planner/subplanner/worker topology, freshness mechanisms, constraints over instructions, accepting a steady error rate, and five swarm coordination failure modes with fixes) live on [Long-running agent swarms](long-running-agent-swarms.md).

- **Agentic MapReduce.** For whole-codebase tasks where a result is only trustworthy if every file was considered (security scanning, breaking-change detection, code-quality enforcement, large-scale migration), a single search-driven agent burns most of its budget just *finding* the relevant code, and its context becomes a shared bottleneck as the run grows because unrelated discoveries keep competing for attention. Agentic MapReduce inverts classic MapReduce: an agent still decides what matters (**Plan**, authoring inspectable, version-controllable "selectors" — Tree-sitter queries, symbol/type queries, import-graph traversals, lexical patterns for repo-specific conventions), but the selector then runs deterministically over the entire repo with no model in the loop (**Shard**), producing a finite, bounded work queue instead of an open-ended search. Each shard is investigated by a fresh, focused worker in parallel (**Map**), and a final Reduce agent dedupes, reconciles, and composes cross-shard relationships — such as chaining an unauthenticated ID leak with an ID-gated RCE into one severe finding, or grouping migration call sites under the API change that caused them. Coverage is guaranteed by construction (the pipeline is complete only when the deterministic queue is exhausted) and cost tracks the volume of *relevant* code rather than repo size, since the Reducer also reasons over compressed per-shard conclusions rather than full transcripts. [Devin Security Swarm](../tools/devin.md) is the first production instance, adding a fifth **Verify** stage that reproduces serious findings in a sandbox; re-runs after the initial Plan only reprocess files changed since the last scan. *Source: Cognition/Devin engineering blog (2026-07-14)*
- **Sidekick multi-model harness.** Run two parallel, fully capable agents on the same task: a frontier model and a cheaper "sidekick" model, each with its own tools and its own persistent, separately-cached context. The frontier model takes minimal actions itself — it plans, interprets ambiguity, and does final review — while delegating mechanical or well-scoped subtasks to the sidekick; a lightweight classifier can reassign which model is "in charge" mid-session. Unlike a single model calling a "smart friend" or advisor tool per-query, which pays an expensive cache-miss cost on every cross-model call because the invoked model's context isn't shared in a cacheable way, the sidekick pattern keeps both models' contexts persistently cached and times any model switch to coincide with a context-compaction boundary — a point that would trigger a cache miss anyway — so the switch is effectively free. Devin Fusion reports holding frontier-level performance at 35% lower cost on a cost-aware coding benchmark (41% with a stronger base model), and drove 88% of one company's internal merged PRs entirely automatically. Contrast with the escalate-on-demand [Advisor strategy](advisor-strategy.md), which shares one persistent executor and calls a second model only per-decision rather than running two persistent agents in parallel. *Source: Cognition/Devin engineering blog (2026-06-29)*
- **Scripted subagent orchestration (orchestration as code).** The model writes the orchestration program for a large task, and the program, not the conversation, decides which subagents run, in what order, and with what prompt. This is more reliable than relying on prompt pressure to make the model remember to spawn separate verifiers. By October 2026 three products ship it: Claude Code's dynamic workflows, [Claude Managed Agents](../tools/claude-managed-agents.md)' "flows" (the API version, up to 1,000 agents per run), and [Devin](../tools/devin.md) Dynamic Workflows. Devin's version shows what the code buys. The script is deterministic Python: `agent()` returns output shaped by a JSON schema, which becomes the next stage's prompt; `pipeline()` streams items through stages with no barrier; `parallel()` waits for every result. Each agent call is recorded under a hash of its prompt and settings, so an interrupted run re-executes the script from the top and finished agents replay instantly. That only works if the script never depends on the clock, randomness, or the filesystem; anything that looks at the outside world goes inside an `agent()` call. Use it for wide fan-out with a combine step (roughly five or more independent units) or a staged pipeline such as audit → fix → verify. Stay with one or two sessions for mechanical codemods, tightly coupled work, or small sequential tasks.
- **Field Guide: self-authored shared context.** A folder owned entirely by the agents themselves, whose index file is automatically injected into every new agent at start; agents alone decide what goes in it, under a line-budget constraint. Modeled on stigmergy (how ants/termites coordinate by modifying their shared environment rather than communicating directly) — since model weights are frozen, capturing genuine surprises for the next agent's trajectory is the mechanism's whole value.
- **Memory repo as swarm workspace.** Cognition's Agent Memory Repo gives a swarm its own folder inside the user's git-backed [agent memory](../concepts/agent-memory.md): a README with the goal and the rules (measure only with one shared benchmark script so numbers compare, pull and read the shared files before each step, record what was ruled out, ask when another agent's area might explain what you see), a shared `findings.md`, a `questions.md` where agents ask each other, and one notes file per agent. In the worked example four agents chasing a p99 latency spike each saw one unexplained symptom; the cause (a cache refresh triggering garbage-collection freezes that exhausted the database pool) appeared only when the questions file connected them. Git is the concurrency control: most commits merge, and when two agents edit the same line the second push is rejected and that agent re-reads both versions before writing. When the swarm ends, one index line in `MEMORY.md` links its folder, so later sessions reuse its benchmark and its lessons. This is the Field Guide's stigmergy made durable across sessions, and it differs from the shared-file locking that failed in Cursor's first swarm ([Long-running agent swarms](long-running-agent-swarms.md)) by letting writes collide and resolving them at push time instead of holding locks. *Source: Cognition, Agent Memory Repo (October 2026)*
- **Control room apart from runtime.** Keep fleet governance in a docs-only folder: which agents exist, what each may and may not do, which credentials each references (never the secrets themselves), runbooks, and backups. An orchestrator reads it to learn what exists and what needs human approval before it routes work, so it is only as good as those docs. Each agent's live state (secrets, memory, skills, sessions, scheduled jobs) stays in its own isolated runtime, which keeps credentials revocable per agent and lets the fleet be rebuilt from the docs: "You can rebuild the body from the brain. You cannot rebuild the brain from the body." Unlike the Field Guide, which the agents write for each other, the operator writes the control room and it governs the agents. *Source: Shann Holmberg's [Hermes Agent](../tools/hermes-agent.md) fleet (May 2026)*
- **Shared task board as the coordination layer.** When many agents across machines and harnesses work one backlog, give them a shared board instead of per-agent Markdown task files: an agent claims a ready task under a lease it must renew, so a stalled agent's work frees itself; tasks declare dependencies, so a review becomes claimable only when its fix completes while independent fixes run in parallel; and replies or label changes wake the agent that owns the thread. The board also holds the original report, findings and PR together, so another agent or a person can review the work, and it syncs with the Slack and GitHub threads people already use. Unlike the memory-repo workspace above, which lets writes collide and settles them at push time, the board assigns ownership before work starts. [Vercel Board](../tools/vercel-board.md) is the first packaged instance; Vercel runs its security-agent swarm and v0's software factory on it. *Source: Vercel (2026-11-18)*
- **Coordinator hub with state in git.** A long-lived coordinator per area of work writes no code: it turns plans into dispatched workers and wakes on events (CI results, review comments, merges, Slack alerts, a schedule) instead of waiting to be prompted. Work is a markdown plan moving through folders in a dedicated repo (`drafts/` → `next/` → `open/` → `done/` or `discarded/`): a high-reasoning model writes the plan until a worker can implement it without design questions, and a fast model executes it. Coordinators cannot message each other, so they leave inbox files in git, each headed From/To/Date/Why, and only a Hub writes into an area's file. Each coordinator commits its notes every turn, which makes it replaceable: after a platform bug looped one coordinator at about 460 messages, a fresh one rebuilt its state from the repo in one turn. It extends mayor + polecats with event subscriptions and git-held state. *Source: Fatih Arslan running [Cursor](../tools/cursor.md) Projects (September 2026)*
