# Authoring Guide — Ingesting a Large, Dense Source

Read this **before** drafting a proposal for any raw source where a single flat proposal cannot show, in full, both (a) every heading/table/bullet's destination and (b) the actual near-final content landing there — without resorting to compressed summary bullets ("both bank accounts... with full detail"). A compressed bullet is a promise of completeness, not something the user can verify — `proposal_template.md`'s Proposed Actions section requires the actual draft markdown/turtle to exist *in the proposal*, not be written for the first time after approval and checked only retroactively by Phase 3's audit.

**Trigger:** the source has more than ~3-4 major sections, each carrying substantial tabular/structured detail (contact lists, account details, compliance calendars, per-item specs), such that one proposal's Proposed-Actions section would need one line per table row to stay honest — typically anything past a few hundred lines of dense reference material (corporate/legal records, data dictionaries, large API references, multi-entity structures).

## The pattern

1. **Chunk along the source's own section boundaries — never by line count.** If the source is already divided into numbered/named units (entities, phases, chapters, modules), each unit is one chunk. Never split mid-table or mid-subsection just to hit a size target; an arbitrary cut risks separating a fact from the constraint that governs it.
2. **Resolve shared vocabulary once, up front.** If multiple chunks will reuse the same concepts (e.g. a long "State of AI" report where every section names a "benchmark," a "license model," a "context-window size"), do the Terminology Reconciliation and open any needed VCR(s) **before** the first chunk's proposal, scoped to the whole source — not per-chunk. Re-deriving the same vocabulary decision six times wastes review effort and risks drift between chunks (chunk 3 quietly inventing a slightly different property than chunk 1 used for the same concept).
3. **One proposal per chunk, with both an extraction map AND the full draft content.** These are two different documents doing two different jobs — neither substitutes for the other:
   - An **Extraction Map** table, one row per heading/table/paragraph in that chunk's source range, mapping it to a destination (which section, which triple/individual pattern) or an explicit "narrative only, no RDF — because <reason>". This proves *coverage* — that nothing was silently skipped.
   - The **full draft content** itself, per `proposal_template.md`'s Proposed Actions section — the complete markdown page (frontmatter + full body, every table reproduced) and the complete `.ace` sidecar (controlled English — not `.ttl`, which is compiled from it), exactly as they'd be committed. This is what the user actually reads to approve. The extraction map tells you *where* everything went; the full draft is the only way to verify *what it actually says* once it got there — a correct-looking map row can still hide a wrong or thinned-out landing.

   Do not treat the extraction map as a lighter-weight replacement for the full draft, and do not treat the full draft as removing the need for the map — a full draft without a map can still silently omit a whole subsection without anyone noticing during review; a map without the full draft can't be checked for accuracy at all (this was the exact gap that prompted writing this guide).
4. **If the full draft is still too large to review as one chunk, split further** — sub-chunk by the source's own next-smaller structural boundary (e.g. one entity's bank accounts + financing separately from its advisors + compliance), rather than compressing the draft to fit the chunk. Chunk size is chosen to keep the *draft* reviewable, not just the extraction map.
5. **Run the full Phase 1–5 loop per chunk**, not once for the whole source: clean-tree check → chunk's proposal (map + full draft) → **mandatory stop for approval** → commit the already-drafted content (extraction is now a copy/paste of the approved draft, not a fresh write) → Phase 3 sub-agent fidelity audit scoped to just that chunk's source line range → Phase 4 auto-correction if needed → Phase 5 final commit. Only then start the next chunk's clean-tree check. This keeps each Phase 3 audit's job tractable and gives the user a natural place to redirect before the remaining chunks inherit a bad pattern.
6. **Process chunks in source order** unless the source's own structure implies a dependency order (e.g. a parent entity before the children that reference it as parent) — those two orderings usually coincide.
7. **Cross-chunk decisions carry forward automatically.** If chunk 1's proposal resolves a contradiction or reuse decision (e.g. "reuse existing IRI X for this recurring real-world thing"), later chunks apply it without re-asking — restate it briefly in the later chunk's Contradictions section for the record, but don't re-litigate.
8. **Name chunk proposals so their sequence and source are obvious**: `proposals/YYYY-MM-DD-<source-slug>-<NN>-<chunk-slug>.md` (e.g. `2026-07-15-state-of-ai-report-01-frontier-models.md`). Move each to `proposals/applied/` on its own completion, same as any other proposal — don't wait for the whole source to finish.
9. **Grep-verify every upstream/inherited property you promised, not just new vocabulary (a lesson from the source project this guide was ported from).** The Extraction Map's per-row destination check reliably catches missing *new* terms (an unresolved gap is visible). It does **not** catch a missing *upstream or inherited* fact — if Terminology Reconciliation lists `aiw:scoreUnit`/`aiw:asOf` as "will be used" for every benchmark result, a result individual quietly missing one of them produces no gap, no flag, nothing for the map to catch, because the property needed no VCR and so triggered no forcing function. Before calling a chunk's draft done, for every upstream/inherited property listed as reused, grep the draft to confirm every individual of the relevant type actually carries it — the same way a code reviewer greps for a promised call site actually being made, not just declared as a plan.

## What this is not

This is not license to under-model a chunk once inside it — every rule in `AGENTS.md` (Rules 5/9/10, the mandatory proposal sections) still applies in full **per chunk**. Chunking controls the unit of review and audit; it does not lower the fidelity bar within that unit.
